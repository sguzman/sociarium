## Direct observations

### Current UI location

The current observed web UI exposes Likes under:

`/i/history/likes`

This differs from the older profile-tab model.

The History shell also exposes Bookmarks alongside Likes, but Bookmarks were not opened during this capture.

### Likes request family

The Likes data itself used the ordinary X GraphQL family:

`https://x.com/i/api/graphql/{queryId}/Likes`

Observed details:

- method: `GET`;
- operation: `Likes`;
- observed query ID: `XHn_Tw60c6pi0n3DGhpwiA`;
- status: 200 on all four observed requests;
- query parameters included `variables`, `features`, and `fieldToggles`;
- requested count: 20.

Observed variable names on the initial request:

- `userId`;
- `count`;
- `includePromotedContent`;
- `withClientEventToken`;
- `withBirdwatchNotes`;
- `withVoice`.

Pagination requests added:

- `cursor`.

Observed field toggles included:

- `withPayments`;
- `withArticlePlainText`.

The query ID is a dated observation, not a durable constant.

### Response envelope

The Likes response used:

`data.user.result.timeline.timeline.instructions`

Each observed page contained one `TimelineAddEntries` instruction.

Each page contained:

- 20 `TimelineTimelineItem` entries carrying primary Post results;
- one Top `TimelineTimelineCursor`;
- one Bottom `TimelineTimelineCursor`.

No terminal instruction was reached in this bounded capture.

### Pagination behavior

Four Likes requests were observed:

1. initial request with no cursor;
2. second request with `variables.cursor`;
3. third request with `variables.cursor`;
4. fourth request with `variables.cursor`.

For every follow-up request, the request cursor exactly matched the previous response's Bottom cursor.

The same `Likes` operation/query ID was reused across all four pages.

Observed primary Post counts:

- page 1: 20;
- page 2: 20;
- page 3: 20;
- page 4: 20.

Across the four pages:

- 80 primary Post entries were observed;
- all 80 primary Post IDs were unique;
- no cross-page duplicate primary Post IDs were observed.

No attempt was made to exhaust the Likes history, so terminal behavior and total reachable depth remain unknown.

### Semantic confirmation

All 80 primary Post results in this Likes timeline had:

`legacy.favorited = true`

This directly confirms that the captured `Likes` operation is serving the account's liked-Post view rather than merely a generic timeline with a misleading UI label.

The returned Post objects otherwise use the familiar X Post result shape, including stable `rest_id` identity and legacy Post fields.

### Per-Post relationship/state fields

Primary Post legacy objects directly included fields such as:

- `favorited`;
- `favorite_count`;
- `bookmarked`;
- `bookmark_count`;
- `retweeted`;
- `retweet_count`;
- `conversation_id_str`;
- `user_id_str`;
- `full_text`.

These are observations of response structure, not a claim that all fields are always present in every Post subtype.

### Auth/session-related names

The Likes GraphQL requests directly contained these header names:

- `x-client-transaction-id`;
- `x-csrf-token`;
- `x-twitter-active-user`;
- `x-twitter-auth-type`;
- `x-twitter-client-language`.

Values are intentionally omitted.

As in the earlier Edge 153 captures, the browser's sanitized HAR omitted ordinary `Cookie`, `Authorization`, and response `Set-Cookie` headers but retained non-empty `x-csrf-token` values.

Therefore this sanitized HAR remains private evidence and is not safe to publish as-is.

## Confirmed/refined baseline claims

This capture directly confirms that, for the observed current X web client:

- Likes are exposed in the UI under `/i/history/likes`;
- the data operation is still named `Likes`;
- the operation uses the standard `/i/api/graphql/{queryId}/{operationName}` family;
- Likes pagination uses opaque Bottom cursors passed through `variables.cursor`;
- the same operation/query ID is reused across successive pages;
- Likes return ordinary Post objects with stable Post identities;
- the primary returned Posts are explicitly marked `favorited = true`.

The UI's relocation of Likes into History does **not** imply a new History-specific data protocol family for the liked Posts themselves.
