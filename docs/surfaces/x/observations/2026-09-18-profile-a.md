## Capture scope caveat

The HAR does not begin on the operator's own profile. It begins with an X `/home` load and includes Home timeline pagination before the own-profile operations appear.

That is useful incidental evidence, but it means this capture does **not** satisfy the own-profile pagination part of Capture A. The profile itself produced one `UserOriginalsTimeline` request, one `UserByScreenName` request, and a later `TweetDetail` request.

Do not mistake the observed `HomeTimeline` cursor requests for profile pagination.

### Own-profile timeline request

- Method: `GET`
- Operation: `UserOriginalsTimeline`
- Query parameters: `variables`, `features`, `fieldToggles`
- Variable names observed:
  - `userId`
  - `count`
  - `includePromotedContent`
  - `withQuickPromoteEligibilityTweetFields`
  - `withVoice`
- Observed requested count: 20

The `TimelineAddEntries` payload contained ordinary Post entries, non-Post modules, and Top/Bottom cursor entries. Consumers cannot safely assume every timeline entry is a Post.

### Profile lookup request

- Method: `GET`
- Operation: `UserByScreenName`
- Query parameters: `variables`, `features`, `fieldToggles`

The capture therefore strengthens the existing Sociarium rule that a mutable screen name should not be the stable profile identity.

Therefore the current repost representation remains **unknown from this capture**. Absence in a bounded sample is not evidence that the web protocol lacks a repost representation.

### Pagination structure

The own-profile response contained `TimelineTimelineCursor` entries with:

- `cursorType = Top`;
- `cursorType = Bottom`;
- an opaque cursor `value`.

However, no second `UserOriginalsTimeline` request carrying that cursor was captured. Therefore:

- cursor response structure: directly observed;
- own-profile next-page request semantics: not yet observed;
- terminal-cursor behavior: unknown;
- profile history depth: unknown.

Incidental Home-feed evidence showed that later `HomeTimeline` POST bodies add a `variables.cursor` field while reusing the same `HomeTimeline` operation/query ID. This must not be generalized to `UserOriginalsTimeline` until directly observed there.

### Sanitized-HAR security finding

Important: the Edge 153 "sanitized" HAR still contained **non-empty `x-csrf-token` values** on X requests.

Therefore an Edge sanitized HAR must still be treated as private authority-bearing evidence. "Sanitized" does not mean safe to publish.

The raw HAR remains private and is not committed.

## Confirmed baseline claims

This capture strengthens the baseline claims that:

- X Web uses `/i/api/graphql/{queryId}/{operationName}`;
- operation names and query IDs are explicit in request paths;
- `UserByScreenName`, `TweetDetail`, and `HomeTimeline` are current first-party operations;

- `x-csrf-token` is present by name on current authenticated web requests;
- internal REST-like request families coexist with GraphQL.

## Baseline corrections / refinements

Public technical references in the baseline commonly identify a profile timeline operation named `UserTweets`.

For this specific 2026-09-18 Edge/X build and observed profile action, the actual operation was **`UserOriginalsTimeline`**.

This does not prove `UserTweets` no longer exists. It does prove that Sociarium must not treat `UserTweets` as the timeless universal profile-timeline operation.

The observation also directly confirms `note_tweet` in the current web payload, despite separate official-API naming drift questions recorded elsewhere in the X dossier.
