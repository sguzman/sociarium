# Bluesky export, migration, and recovery

Research date: 2026-09-18.

## Repository export

AT Protocol repositories can be exported as **CAR files**.

Official repository documentation describes CAR exports as suitable for:

- synchronization;
- offline backup;
- migration.

The repository is content-addressed and signed. This provides substantially stronger provenance than an ad hoc JSON archive generated by an opaque platform export job.

## Blobs

Media blobs are referenced by CID from repository records but stored separately by the PDS.

A complete practical account backup therefore needs both:

1. repository CAR data;
2. referenced blobs.

Official recovery guidance includes separate repo and blob export steps.

## Preferences

Private Bluesky application preferences are not assumed to live inside the public signed repository.

Official migration documentation exports preferences through authenticated application APIs and restores them separately.

This reinforces a central Sociarium distinction:

> Complete repository portability is not identical to complete service-account portability.

## PDS migration

Official documentation treats movement between Personal Data Servers as a supported workflow.

Migration includes:

- fetching/exporting the repository;
- moving blobs;
- moving private preferences where applicable;
- updating identity/account routing;
- importing repository state to the new PDS.

The stable DID can remain the identity while the hosting PDS changes.

## Adversarial recovery

AT Protocol's recovery design explicitly considers an unavailable or uncooperative PDS.

Official guidance recommends backups and explains how a user with the necessary identity rotation authority can migrate/recover.

This is unusually aligned with Sociarium's anti-hostage objective.

## Identity recovery nuance

For `did:plc`, identity-control recovery depends on rotation-key authority.

Default hosted-account arrangements do not mean every user automatically self-custodies every identity-control key. Users who want stronger independence can manage an additional rotation key, but doing so introduces real operational responsibility.

Sociarium should describe this accurately rather than using "decentralized" as a magic synonym for "nothing can ever be held hostage."

## Practical backup model

Official tooling examples support a backup model conceptually like:

```text
repo CAR
+ blob export
+ private preferences export
+ any separate service-specific private state
= stronger account backup
```

This is one of the strongest portability foundations in the initial Surface Atlas.
